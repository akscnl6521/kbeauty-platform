# 02. Project Rule — K-Beauty Match 프로젝트 규칙

이 문서는 K-Beauty Match(글로벌 AI 스킨케어 추천 플랫폼)의 미션·비전·개발·보안·확장에 대한 **공통 규칙**이다.  
모든 기여자와 AI 어시스턴트는 코드·문서·설계 변경 시 이 규칙을 우선 적용한다.

---

## 1. Project Mission

K-Beauty Match의 미션은 다음과 같다.

- 전 세계 사용자가 **자신의 피부에 맞는 한국 스킨케어**를 쉽고 신뢰할 수 있게 찾도록 돕는다.
- 설문, 얼굴 부위 탐색, AI 분석을 통해 **개인화 추천의 진입 장벽**을 낮춘다.
- 제품·성분·추천 이유를 연결해 **근거 있는 선택**을 지원한다.
- 영어·일본어·한국어를 기본으로 **글로벌 접근성**을 유지한다.

미션에 반하는 기능(예: 의료 진단 대체 주장, 근거 없는 과장 추천)은 추가하지 않는다.

---

## 2. Vision

### 단기 비전

- 퀴즈·AI 분석·성분 정보가 **하나의 추천 경험**으로 자연스럽게 이어지는 MVP를 완성한다.
- 브라우저 중심 구조의 보안·성능 리스크를 줄이고, **서버 API 계층**으로 전환한다.

### 중장기 비전

- AI 결과가 단순 배지가 아니라 **제품 랭킹·루틴·성분 매칭**에 실제로 반영된다.
- 계정 기반으로 즐겨찾기·분석 이력이 동기화된다.
- 의미 검색·대화형 탐색 등 **고도화된 개인화**로 확장한다.

### 비전 정렬 원칙

- 새 기능은 “사용자 피부 이해 → 적합한 제품/성분 발견 → 신뢰할 수 있는 이유 제시” 흐름을 강화해야 한다.
- 브랜드·제품명·포지셔닝이 문서와 UI에서 충돌하면, 확정 전까지 임의로 바꾸지 않고 `docs`에 TODO로 남긴다.

---

## 3. Development Principles

1. **이해 먼저**: 대규모 변경 전 기존 구조(`src/app`, Supabase, AI, i18n)를 파악한 뒤 작업한다.
2. **범위 최소화**: 요청한 작업만 수행한다. 무관한 리팩터링·파일 정리는 하지 않는다.
3. **문서 동기화**: 아키텍처·DB·AI·API가 바뀌면 관련 `docs/*.md`를 함께 갱신한다.
4. **확정 전 TODO**: 미확정 사항은 추측으로 고정하지 말고 `TODO`로 명시한다.
5. **클라이언트 → 서버 이행**: 현재는 클라이언트 직접 호출이 많으나, 신규 민감 로직은 서버(API Route)를 우선 검토한다.
6. **기존 패턴 존중**: 새 추상화·라이브러리 도입보다 저장소의 기존 패턴을 따른다.
7. **동작 검증**: 변경 후 관련 페이지·필터·다국어·데이터 로딩이 깨지지 않는지 확인한다.
8. **한국어 커뮤니케이션**: 사용자 대면 설명·문서는 한국어를 기본으로 한다.

---

## 4. Coding Standards

### 일반

- TypeScript를 사용하고, 타입을 느슨하게 `any`로 우회하지 않는다.
- 경로 별칭 `@/*` → `src/*` 규칙을 따른다.
- 주석은 “왜”가 필요할 때만 짧게 작성한다. 설명용 장문 주석·불필요한 나레이션을 넣지 않는다.
- 사용하지 않는 import·변수·데드 코드를 남기지 않는다.

### Next.js / React

- App Router(`src/app`)만 사용한다. Pages Router를 새로 도입하지 않는다.
- 서버에서 가능한 일은 서버에서 처리하는 방향을 지향한다. 단, 기존 `"use client"` 페이지를 일괄 전환하지 말고 필요 시점에 점진적으로 한다.
- API가 필요하면 `src/app/api/**/route.ts` 형태로 추가한다.
- `middleware.ts`는 인증·locale 등 명확한 목적이 있을 때만 도입한다.

### 스타일 / UI 코드

- 기존 색·타이포·레이아웃 톤을 유지한다.
- 요청 없이 디자인 시스템을 전면 교체하지 않는다.
- 인라인 스타일과 Tailwind 유틸이 혼재할 수 있으나, 한 파일 안에서는 가독성 있게 일관되게 작성한다.

### 다국어

- 지원 로케일: `en`, `ja`, `ko`.
- 공통 문구는 `src/locales/*.json`과 `useLocale` 사용을 우선한다.
- 화면마다 번역 로직을 복제하기보다, 가능하면 공통 키로 통합한다.
- UI 문자열을 하드코딩할 경우 3개 언어를 함께 고려한다.

### 금지

- 시크릿을 소스에 하드코딩하지 않는다.
- 요청 없이 의존성을 대량 추가하지 않는다.
- 생성 DB 타입이 도입되기 전까지 테이블 컬럼을 임의로 가정해 깨지는 쿼리를 넣지 않는다. 불확실하면 TODO로 표시한다.

## 5. Database Rules

1. **단일 진실 원천**: 제품·성분 마스터 데이터는 Supabase(PostgreSQL)에 둔다.
2. **클라이언트 접근**: 브라우저에서는 anon 키만 사용한다. 서비스 롤 키는 클라이언트에 노출하지 않는다.
3. **RLS 필수**: 테이블 공개 범위는 RLS 정책으로 제어한다. anon 읽기 허용은 의도적으로 문서화한다.
4. **스키마 변경 절차**:
   - `supabase/migrations/`에 마이그레이션을 추가한다.
   - `docs/04_DB.md`를 갱신한다.
   - 앱 코드의 select 컬럼·타입 선언을 함께 맞춘다.
5. **다국어 컬럼**: 사용자에게 보이는 텍스트는 `*_ko`, `*_ja`, 기본(영문) 컬럼 패턴을 따른다. 새 텍스트 컬럼 추가 시 3개 언어를 함께 설계한다.
6. **대량 로드 지양**: 클라이언트에 수천~수만 행을 통째로 내려 필터링하는 방식은 점진적으로 서버 필터·페이지네이션으로 대체한다.
7. **사용자 데이터**: 즐겨찾기·분석 결과를 DB에 저장할 경우, 사용자 식별·삭제·보관 기간을 함께 정의한다.
8. **추측 금지**: 저장소에 없는 테이블/컬럼을 “있을 것”으로 가정하고 배포하지 않는다.

---

## 6. AI Rules

1. **역할 한정**: AI는 피부 이해 보조·추천 힌트·설명 생성에 사용한다. **의료 진단·처방·치료 대체**로 표현하지 않는다.
2. **키 보호**: Anthropic 등 AI API 키는 서버 환경변수로만 사용한다. `NEXT_PUBLIC_` 노출·브라우저 직접 호출은 신규 구현에서 금지하며, 기존 구현은 서버 API로 이전하는 것을 우선 과제로 한다.
3. **출력 검증**: 모델 응답은 스키마(필수 필드, 허용 enum)를 검증한 뒤 UI에 반영한다.
4. **추천 연결**: AI 결과는 가능하면 제품 필터/랭킹/성분 매칭에 연결한다. `ai=1` 배지만 추가하는 방식은 지양한다.
5. **투명성**: 사용자에게 AI가 관여했음을 과장 없이 표시하고, 한계(추정·참고용)를 명확히 한다.
6. **개인정보**: 얼굴 사진·피부 정보는 민감 정보로 취급한다. 불필요한 서버 영구 저장을 하지 않으며, 저장 시 목적·기간·삭제를 정의한다.
7. **비용 통제**: 모델·토큰·호출 빈도·캐시를 고려한다. 동일 입력 재호출을 줄인다.
8. **프롬프트 관리**: 시스템 프롬프트·출력 포맷 변경 시 `docs/05_AI.md`에 반영한다.
9. **안전 가드레일**: 유해·불법·의료 과잉 주장 응답을 유도하는 프롬프트를 넣지 않는다.

---

## 7. UI/UX Principles

1. **한 화면 한 목적**: 섹션마다 목적·헤드라인·짧은 설명을 명확히 한다.
2. **브랜드 우선**: 랜딩 첫 뷰포트에서 브랜드/제품 정체성이 드러나야 한다. 헤드라인이 브랜드를 압도하지 않게 한다.
3. **히어로 절제**: 첫 화면은 브랜드, 핵심 메시지, 짧은 보조 문장, CTA, 주 비주얼 중심으로 구성한다. 통계·프로모 칩·카드 나열로 첫 화면을 채우지 않는다.
4. **실사용 동선**: 퀴즈 → 결과, 분석 → 결과, 얼굴 탐색 → 결과처럼 **추천으로 이어지는 경로**를 끊지 않는다.
5. **다국어 UX**: 언어 전환 후에도 레이아웃이 깨지지 않게 한다. 번역 누락 시 빈 문자열을 노출하지 않는다.
6. **피드백**: 로딩·빈 결과·오류 상태를 사용자가 이해할 수 있게 표시한다.
7. **모바일 우선 검증**: 데스크톱과 모바일 모두에서 주요 동선이 동작해야 한다.
8. **접근성 기본**: 버튼/링크는 클릭 가능 영역과 대비를 확보하고, 이미지에는 의미 있는 대체 텍스트를 고려한다.
9. **기존 톤 유지**: 크림/퍼플 그라데이션 등 범용 템플릿 룩으로 전면 재디자인하지 않는다. 현재 비주얼 언어를 존중한다.
10. **카드 남용 금지**: 상호작용에 필요하지 않은 카드·배지·플로팅 라벨을 히어로에 올리지 않는다.

## 8. Git Commit Rules

1. **명시적 요청 시에만 커밋**: 사용자가 커밋을 요청하기 전에는 커밋하지 않는다.
2. **커밋 메시지**: 변경의 “왜”를 1~2문장으로 명확히 쓴다. (예: 기능 추가 / 버그 수정 / 문서 갱신)
3. **관련 파일만 스테이징**: 시크릿(`.env`, 키 파일), 무관한 로컬 변경을 섞지 않는다.
4. **훅 존중**: pre-commit 실패 시 `--no-verify`로 우회하지 않는다. 원인을 고친 뒤 새 커밋을 만든다.
5. **파괴적 명령 금지**: `push --force`, hard reset 등은 사용자가 명확히 요청한 경우에만 한다. `main`/`master` force push는 특히 경고한다.
6. **amend 제한**: 사용자가 요청했고, 해당 HEAD가 이번 대화에서 만든 커밋이며, 원격에 푸시되지 않은 경우에만 검토한다.
7. **푸시**: 사용자가 요청하기 전에는 원격에 push하지 않는다.
8. **문서 전용 변경**: `docs/`만 바뀐 경우 커밋 메시지에 문서 갱신임을 분명히 한다.

---

## 9. Security Rules

1. **시크릿 분리**: API 키·서비스 롤 키는 환경변수로만 관리하고 저장소에 커밋하지 않는다.
2. **공개 환경변수 인식**: `NEXT_PUBLIC_*`는 브라우저에 노출된다. 비밀 키에 사용하지 않는다.
3. **최소 권한**: Supabase는 필요한 읽기/쓰기만 RLS로 허용한다.
4. **입력 검증**: 사용자 입력·AI 응답·URL 쿼리(`tone`, `concern`, `budget` 등)를 신뢰하지 말고 검증·정규화한다.
5. **민감 데이터**: 얼굴 이미지·피부 분석 결과는 전송 최소화, 저장 최소화, 삭제 가능 원칙을 따른다.
6. **의존성**: 출처 불명 패키지·불필요한 권한 확대를 피한다.
7. **법적 페이지**: 개인정보·약관과 실제 데이터 처리가 어긋나면 기능을 추가하기 전에 정책을 맞춘다.
8. **보안 이슈 우선**: 키 노출·RLS 미비·인증 우회 등은 기능 추가보다 우선 수정한다.

---

## 10. Future Expansion Principles

1. **점진적 확장**: 빅뱅 재작성보다, 동작하는 MVP 위에 계층을 쌓는다.
2. **API 우선 확장**: 인증, AI, 추천 스코어링, 결제/제휴 등 민감·공유 로직은 API/서버 계층에 둔다.
3. **데이터 모델 먼저**: 새 도메인(계정, 즐겨찾기 서버화, 벡터 검색)은 테이블·RLS·문서를 정한 뒤 UI를 붙인다.
4. **추천 품질 중심**: 새 AI 기능은 “예쁜 데모”보다 **제품/루틴 결정에 미치는 영향**으로 평가한다.
5. **관측 가능성**: 확장 시 로깅·오류 추적·비용 모니터링을 함께 설계한다.
6. **국제화 확장**: 새 언어 추가 시 URL·메타·DB 컬럼·번역 키 전략을 한 세트로 정의한다.
7. **하위 호환**: URL 쿼리·localStorage 키·공개 API를 바꿀 때는 마이그레이션/폴백을 제공한다.
8. **폐기 명확화**: 구식 경로(예: 브라우저 직접 AI 호출)는 대체 구현 후 제거하고 문서에서 deprecated로 표시한다.
9. **비즈니스 정렬**: 커머스·제휴·광고 확장은 추천 신뢰도를 해치지 않는 선에서만 도입한다.
10. **결정 기록**: 큰 기술 선택은 `docs`에 근거와 대안을 남겨, 이후 기여자가 같은 논쟁을 반복하지 않게 한다.

## 부칙: 규칙 적용 우선순위

충돌 시 다음 순서를 따른다.

1. 보안·개인정보
2. 사용자 신뢰(과장 금지, 근거 있는 추천)
3. 이 문서의 명시 규칙
4. 관련 `docs` (Architecture, DB, AI, API, Roadmap)
5. 기존 코드 관례
6. 편의성·속도
